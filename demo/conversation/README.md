# Natural Language Actor-to-Actor Communication Demo

Proves that independent CognitiveOS Actors can hold a real
conversation — not just get routed to react in sequence — to
collaboratively answer a customer's question. Five Actors (Customer,
Warehouse Worker, Inventory Robot, Driver, Support Agent) exchange
plain-English messages; each reply is generated by that Actor's own
independent reasoning over real world state, not by a script, a
template, or a central planner deciding what everyone says.

## What it proves — and what it doesn't

```
Actor A asks Actor B a question (natural language)
  -> Actor B reasons independently over real world state
  -> Actor B replies in natural language
  -> Actor A (or a third Actor) uses that reply to continue reasoning
  -> repeat across a chain of Actors
  -> a customer request gets answered through dialogue, not a single
     centralized plan
```

**Important, honest limitation**: in every demonstration below, THIS
SCRIPT decides who talks to whom and in what order — `ask(client,
world, "Warehouse Worker", question, from_name="Customer")` is a call
this script writes, not a decision any actor makes. Every reply is
real (independent LLM reasoning, grounded in real world state, fully
verified — see `expected_output.md`), but the routing around those
replies is scripted, not autonomous. That's a real gap, raised
directly: an actor never decides for itself that it lacks information,
never chooses who to ask, never decides when it knows enough to stop.
**`demo/dialogue/` closes that gap** — there, the Support Agent's own
LLM planner makes all three of those decisions as real plan steps
(`AskActorCapability`/`RespondToInquiryCapability`); this script here
proves the reasoning and reply generation are real, `demo/dialogue/`
proves the *conversation* — who talks to whom — is too.

## The real gap this demo required closing

The coordination engine built for the previous sprint (`demo/coordination/`)
proves Societies react to real domain events — but nothing in the
codebase let one Actor ask another a free-form question and get back
genuine natural-language reasoning. Confirmed before writing any of
this: `POST /prompt`'s `answer` field was a fixed template
(`f"{question} executed through the planetary cycle"`), not real LLM
output; every existing capability returns a structured business dict,
never a sentence; `ContextStream` is broadcast-only with no addressed
reply routing. Closing this gap required one small, real addition —
not a demo-only fake:

- **`AnswerQuestionCapability`** (`kernel/domains/grocery.py`, registered
  in `build_default_capability_bus()`) — given a question, it gathers
  real facts via the exact same keyword-matched KG lookup
  `ContextConstructionEngine._explore_knowledge()` already uses for
  planning (`kg.entities_by_keywords()`, `kg.connected_entities()` —
  nothing reinvented), formats them with full real attributes, and
  makes one real LLM call (`get_backend().complete()` — the same
  backend `LLMPlanner` uses) asking for a short, grounded,
  conversational reply. Returns `{"success": True, "answer": "<real
  LLM text>"}` — the first capability in this codebase whose result is
  natural language, not a structured dict.
- **`POST /actors/{actor_id}/ask`** (`api/routes/actors.py`) — the real
  endpoint this demo calls. Looks up the actor's real registered name/
  goals/society, invokes `AnswerQuestionCapability` directly (an API-
  driven deterministic call, same convention `POST /orders` uses to
  invoke `OrderCreationCapability` directly rather than requiring the
  planner to select it — reliability, not a shortcut around real
  reasoning: the capability that runs is fixed, but everything it
  produces is genuinely generated), and publishes a real
  `ContextEvent` (`INTERACTION` type) recording sender, recipient,
  society, and the real question/answer for explainability.

## What this demo script does — and does NOT do

This script (`run_conversation.py`) is the **only** thing that relays
one actor's answer into the next actor's question — by reading the
real text `POST /actors/{id}/ask` returned and passing it, as plain
text, inside the next call's `question` field. There is no hidden
inter-actor channel in the runtime; any external client could
reproduce this exact conversation with five separate HTTP calls, each
one waiting for the previous real response.

What's real: every fact any actor states (stock count, price, order
ID, shipment status, tracking number, rider assignment) is read live
from the KG at the moment of that call — see
[`expected_output.md`](expected_output.md) for a live cross-check
against `GET /shipments/{id}` proving the tracking number an actor
"remembered" was genuinely retrieved, not invented. What's NOT
claimed: the *exact wording* of every reply is not reproducible
between runs (it's real LLM output) — what's reproducible is that
every reply stays grounded in the real facts available at that moment.

## Running it

```bash
cd demo/conversation
python3 run_conversation.py
```

Builds its own isolated world — run against a freshly reset server
(see `demo/ecommerce/README.md`'s reset procedure). `DEMO_BASE_URL`
overrides the default `http://localhost:8031/api/v1/agentos`.

## Demonstrations

1. **Customer and Warehouse** — before any order exists, the Customer
   asks about stock and timing; the Warehouse Worker answers from real
   product facts (quantity, price).
2. **Warehouse and Driver** — after a real order + shipment are created
   via API, the Warehouse Worker tells the Driver it's packed and asks
   about tomorrow delivery.
3. **Negotiation** — the Driver asks for a packing delay; the Warehouse
   Worker responds conversationally, reasoning about the request rather
   than executing a predefined "delay" action.
4. **Information request** — Customer asks Support Agent, who doesn't
   know and asks the Warehouse Worker in turn, then relays the
   Warehouse Worker's real answer back to the Customer in its own
   words.
5. **Multi-actor collaboration** — one customer question
   (`Can this order arrive tomorrow?`) is answered by chaining real
   replies through Warehouse Worker -> Inventory Robot -> Driver ->
   Support Agent, each one reasoning over the previous actor's real
   answer plus its own real facts, ending in a synthesized answer to
   the customer that no single actor produced alone.

## Explainability

Every exchange prints, for real:

```
Sender
    ↓
Society
    ↓
Recipient
  Sender ....... <name>
  Recipient .... <name>
  Society ...... <name>
  Timestamp .... <HH:MM:SS>
```

`Society` comes from the real Society the recipient belongs to
(`SocietyRuntime.society.name`, looked up the same way every other
route in `actors.py` does it — not asserted). `Timestamp` is the real
wall-clock time the `ContextEvent` was published.

## Files

- `bootstrap.py` — builds geography, 5 societies, 5 actors (Customer,
  Warehouse Worker, Inventory Robot, Driver, Support Agent), a merchant
  storefront, a product, and a delivery rider — all via real APIs.
  Deliberately does NOT create the order/shipment; `run_conversation.py`
  does that mid-script so each demonstration reasons over a genuinely
  different, evolving world state (pre-order, packed-not-dispatched,
  etc.), the same way `demo/ecommerce/run_demo.py` injects its fire
  event mid-script rather than upfront.
- `run_conversation.py` — the five demonstrations, the real order/
  shipment lifecycle calls between them, and the relay logic described
  above.
- `expected_output.md` — a real captured transcript with a live
  fact-check against the server proving specific claimed facts (a
  tracking number) were genuinely retrieved, not invented.
